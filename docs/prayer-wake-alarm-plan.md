## Plan: Integrate Prayer Wake Alarms

Integrate Alarm into TunisianPrayerTimes by extracting and adapting its alarm runtime, not by importing the Alarm app module wholesale. Keep the prayer-centric UX, add an independent wake-alarm editor per supported prayer, and support both fixed-time and prayer-relative main alarms plus Alarm-style sub-alarms. Reuse Alarm’s playback/receiver stack, but fit scheduling and data models around TunisianPrayerTimes’s delegation/prayer-time engine and minSdk 26.

**Steps**
1. Phase 1 — carve out the reusable Alarm runtime. Create a new package under TunisianPrayerTimes android-app for wake alarms and port/adapt Alarm’s trigger payload, receiver, playback service, alert activity, stop action receiver, tone/ringtone helpers, and notification plumbing. This blocks the later scheduler and UI work. Do not include Alarm as a Gradle app module because it is an application module with its own Application class, manifest, minSdk 29, and generic alarm-list UI.
2. Phase 2 — define prayer-aware wake models in shared code. Add wake-specific models alongside the shared prayer models: a main wake config, sub-alarm config, and trigger mode enum for fixed-time vs prayer-relative alarms. Support one main wake alarm per supported prayer plus zero or more sub-alarms. The main alarm may be fixed clock time or anchored to that prayer with a signed offset; sub-alarms stay Alarm-compatible and remain relative to the main alarm. For Friday, reuse the DHUHR config but resolve its anchor to the effective Jomoaa time only when the main alarm is prayer-relative; fixed-time alarms must remain fixed-time on Friday as well. This depends on Phase 1 and blocks Phases 3–6.
3. Phase 3 — persist wake configs separately from silence prefs. Introduce a dedicated prayer wake repository backed by DataStore plus JSON serialization rather than extending PrefsManager with a large matrix of flat keys. Keep PrefsManager for the existing silence settings and Jomoaa override time. Store prayer-centric wake configs keyed by prayer identity rather than importing Alarm’s generic list-based persistence model, so the data shape stays aligned with the prayer-row UX. This can start in parallel with Phase 2 once the wake model shape is settled, and it blocks Phases 4–6.
4. Phase 4 — build a prayer-aware wake scheduler. Add a separate WakeAlarmScheduler and, if needed for clean logic reuse, a pure WakeAlarmComputer modeled after SilenceAlarmComputer. Reuse PrayerTimesRepository, PrefsManager’s effective Jomoaa time, and AlarmScheduler’s signed before/after offset logic. Cover today’s alarms, tomorrow’s safety scheduling, midnight reschedule, and distinct pending-intent identity for main alarms vs sub-alarms. Make the trigger computation explicit: use a cross-midnight candidate search window across adjacent prayer dates so negative offsets and before-main sub-alarms can resolve to the previous civil day when needed, then pick the earliest future trigger. This depends on Phases 2–3 and blocks Phases 5–7.
5. Phase 5 — wire lifecycle and platform integration. Update boot/update rescheduling, exact-alarm permission refresh, and periodic verification so wake alarms reschedule even when auto-silence is off. The safest path is either a dedicated WakeAlarmVerifyWorker or a generalized schedule worker that runs when either silence or wake alarms are enabled. Add manifest entries and permissions for playback, foreground/full-screen alarm UI, notifications, and microphone-backed snore tracking. This depends on Phases 1, 3, and 4, and can run in parallel with Phase 6 once interfaces stabilize.
6. Phase 6 — add prayer-centric editing UX. Keep the current prayer list and add a compact wake-alarm summary/control on each supported prayer row in MainScreen; tapping it should open a dedicated bottom sheet or detail editor adapted from AlarmEditorSheet rather than inlining full-parity controls into the existing row. The editor should expose enable/disable, fixed vs prayer-relative main alarm, signed offset input, ringtone choice, vibration-only, wake-up check, progressive volume, snore tracking, and sub-alarm add/edit/remove. Show the feature only on FAJR, DHUHR, ASR, MAGHRIB, and ISHA rows; on Fridays, the DHUHR editor keeps the same config but schedules against Jomoaa time. This depends on Phases 2–4 and blocks Phase 7.
7. Phase 7 — add trigger handling and parity extras. Connect the wake receiver to playback and the full-screen alert activity, add stop actions, and bring over wake-up check, progressive volume, bundled/custom ringtones, and snore tracking after the core alarm path is stable. Reuse Alarm’s trigger payload contract so main alarms and sub-alarms share one service/activity protocol. This depends on Phases 1, 4, 5, and 6.
8. Phase 8 — migration and polish. Ship wake alarms disabled by default, copy the required strings/raw tones/theme resources from Alarm, and audit imported code for minSdk 26 compatibility. Replace any API 29+ assumptions with guards or fallbacks before release. This depends on Phases 1–7.

**Decisions**
- Include: full Alarm-style wake experience, but anchored to prayer rows rather than a standalone generic alarm list.
- Include: supported prayers are FAJR, DHUHR, ASR, MAGHRIB, and ISHA only.
- Include: both fixed-time and prayer-relative main alarm triggers.
- Include: Alarm-style sub-alarms before and after the main wake alarm.
- Include: wake alarms are independent from the auto-silence toggle.
- Include: on Fridays, the DHUHR wake config uses Jomoaa time as its anchor only for prayer-relative alarms; fixed-time alarms remain fixed-time.
- Exclude for this iteration: direct Gradle-module inclusion of the entire Alarm app as-is; the code should be extracted and adapted into TunisianPrayerTimes instead.
- Exclude for this iteration: Eid-specific wake alarm editors.

**Further Considerations**
1. Persistence recommendation: use a dedicated wake-alarm DataStore/repository instead of extending PrefsManager with dozens of new flat keys, because sub-alarms and ringtone URIs are structured data.
2. UI recommendation: keep wake editing in a bottom sheet or detail screen per prayer; full-parity controls will overcrowd the current in-row layout if they are inlined.
3. Scheduling rule: negative offsets and before-main sub-alarms must use a cross-midnight candidate search rather than same-day-only time math, otherwise pre-Fajr and late-night triggers will be missed.
4. Compatibility risk: Alarm currently targets minSdk 29 while TunisianPrayerTimes targets minSdk 26, so imported alarm code must be audited and guarded rather than assumed portable.
