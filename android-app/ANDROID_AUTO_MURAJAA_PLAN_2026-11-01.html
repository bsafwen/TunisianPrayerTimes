Revised proposal · 1 November 2026 · Android Auto only

Use the existing المراجعة in Android Auto

Bring مراجعة اليوم and مراجعة الدفتر to the head unit, using the same saved notebook, questions, corrective practice, self-assessment and scheduling as the phone.

The phone feature is implemented. Its Android Auto adapter is the work proposed here.

Scope: another interface to the same review

The user should be able to start today’s existing review directly in the car, or continue an unfinished one. A new audio-session preparation screen is not a prerequisite. The current due-point selection, notebook order, assistance rules, grades, drills and progress records remain the source of truth.

The central distinction: an explicit assessment in the car applies the same grading and scheduling rules as its phone counterpart. Playing audio, skipping, pausing or reaching the end of a recording never supplies that assessment automatically.

Entry points on the head unit

Add المراجعة under الاستماع, keeping the four main listening tabs stable. Its choices are:

  • تابع المراجعة: resume the current question, reveal/assessment state or corrective drill from the shared unfinished session.
  • مراجعة اليوم: start the same eligible batch that the phone would offer, with no new car-specific scheduler.
  • مراجعة الدفتر: open existing notebook practice, using its existing selection and ordering rules. A phone-selected subset can be handed over through the same session.
  • مواضعي صوتًا: retain the existing listening option as a separate choice. Its playback does not award review grades.

Check the required recordings using the existing download system. Available audio should let the user begin directly. If a cue, answer or requested drill needs a download, retain the session and explain that it can be downloaded on the phone when safe; do not substitute a different question or reciter silently.

The existing question cycle, adapted to audio

1 · Question

Recall before reveal

Use the existing question, for example ماذا بعد الآية 66 من سورة البقرة؟. The optional preceding-verse cue uses the existing recording. Let the user recall at their own pace.

A short spoken navigation prompt may read the question. Quran recitation itself always comes from the verified recording.

2 · Reveal and assess

The same honest answer

اسمع الجواب performs the existing reveal transition and plays the correct passage. Then ask how the recall went before the answer was revealed.

Offer the existing three outcomes. When the engine considers the attempt assisted, preserve its restriction on دون مساعدة.

3 · Correction or next

Keep the current teaching flow

A successful recall follows the existing next-question transition. Hesitation or a mistake offers the existing corrective drill, including its deliberate repetitions and look-alike comparisons.

Finishing the drill is practice. The next scheduled check remains governed by the existing Hifz rules.

The main engineering change: share the session owner

Today, startReview, startPractice, the action implementations and return-to-listening orchestration live inside QuranScreen. HifzReviewState and HifzPracticeState hold their sessions through Compose state and saveable UI state. They cannot simply be invoked by an Android Auto service while that screen is absent.

  1. Extract a shared review coordinator. Move the existing session orchestration out of the composable screen. Keep the existing Hifz models and algorithms. Phone and Auto become adapters to one session owner; visual folding and text-editing drafts remain phone presentation state.
  2. Persist the shared unfinished session. Retain mode, question IDs/order, current attempt, revealed/assisted state, recorded responses, drill state and audio position. Persist the existing semantics, rather than introducing an independent Auto review plan or a second progress ledger.
  3. Route both interfaces through the same commands. Start, cue, reveal, assess, drill, advance, pause and finish must behave identically regardless of which interface sent them. A token for the active question prevents delayed or duplicate car commands from assessing a different question.
  4. Keep repository writes authoritative. Confirmed answers update the existing current notebook point through its grading rules, exactly once. Re-read a point before writing; an edited or deleted point must not be overwritten or resurrected by an old car callback.
  5. Connect the browser and media controls. Add review entry IDs and phase-specific actions. Route Play/Next/Previous to the active review before ordinary listening handlers, so a media button cannot accidentally leave the review and resume a surah queue. Preserve normal listening and its queue. Phone and car can transfer a paused session without creating duplicate reviews or regrading answered cards.

Rules to preserve exactly

  • Due-point eligibility, balanced batches, answer-safe ordering, exposure deferrals and the existing day-change policy.
  • In notebook practice, a due answer counts as review; for a non-due point, only a reported forgotten/mistaken answer changes its plan, as the phone already implements.
  • Help heard before reveal can make the attempt assisted. Hearing the answer after deliberate reveal must not retroactively change an otherwise unaided attempt.
  • Record only audio actually heard. A queued request, download, seek or silent gap is not an exposure.
  • An explicit assessment updates grades and schedules. Playback completion, Next, silence and time spent never infer successful recall.
  • Retain the existing drill behavior and ordinary listening return place. Detailed note editing, word selection and visual comparisons remain accessible on the phone.

Implementation and validation order

  1. Shared-session extraction: move existing orchestration with behavior-preserving tests for today’s review, notebook practice, assisted recall, linked questions and the three outcomes.
  2. One complete car question: prototype question → optional cue → reveal/audio answer → explicit assessment → existing correction or next. Validate the control layout before expanding the browse tree.
  3. Full session and handoff: add start/continue entries, shared persistence, phone handoff, interruption recovery and the existing result summary.
  4. Parity tests: apply identical action sequences through phone and car adapters and compare point changes, due dates, assistance state, deferred IDs and totals. Test duplicate/late actions, deleted points, midnight and service recreation.
  5. DHU and car checks: confirm offline audio, control discoverability, touch/rotary input, calls, DND, alarms and disconnects. Test actual spoken assistant routing separately; do not depend on unverified custom spoken grading commands.
Acceptance: the same review answers produce the same Hifz records and next review dates on the phone and in Auto. An interrupted session resumes consistently. Playback alone records no grade. No mandatory new car-preparation workflow is added.

 531  fun hifzDrill(catalog: QuranCatalog, point: HifzPoint): QuranPlaylist {
 532      val name = { n: Int -> catalog.surahs.getOrNull(n - 1)?.name.orEmpty() }
 533      val own = hifzPassage(point)
 534      val others = point.lookAlikes
 535      val ownLabel = hifzRangeLabel(name(own.from.surah), own)
 536      val (items, labels) = if (others.isNotEmpty()) {
 537          val right = "الصواب · $ownLabel"
 538          val turns = (if (others.size == 1) others + others else others).map { other ->
 539              QuranRepeatRange(other, other, 1) to "الشبيهة · ${hifzRangeLabel(name(other.surah), QuranRepeatRange(other, other, 1))}"
 540          }
 541          (listOf(own) + turns.flatMap { listOf(it.first, own) }) to (listOf(right) + turns.flatMap { listOf(it.second, right) })
 542      } else List(3) { own } to List(3) { ownLabel }
 543      return QuranPlaylist(
 544          title = HifzDrillTitle,
 545          items = items,
 546          labels = labels,
 547          rounds = 1,
