# Mosque silencing — Stage 0 go/no-go report

**Date: 2026-10-28. Decision: NO-GO to proceed with the rest of the plan on the current evidence.** The isolated logic and several Android mechanisms, including actual Modes stop and named permission/idle recovery paths, are feasible on the tested Pixel 6. Real-mosque holding/departure reliability, sustained battery cost and the remaining support/recovery limits are not established. This is an evidence limit, not a finding that the feature is impossible. Stages 1–4 were not started.

**Polygon scope follows the owner's latest instruction:** Tunisia polygons will be ready later; three existing areas were used for tests. Catalog completeness, source-rights review and shipping are not part of this Stage 0 decision. Real-mosque field validation is explicitly **pending at the owner's request**.

## What was built

A separate, debug-only [diagnostic project](stage0-mosque-probe/README.md), application ID `com.tunisianprayertimes.stage0`, compiled with SDK 36 and targeting API 36. It has no dependency on the production app module and does not replace the installed prayer app.

- Pure Kotlin polygon classification, presence states and mode/owner decisions, using the plan's provisional deadlines.
- Three exact Tunisia test shapes: small Ain Soltane, near-median Sousse and large Al-Hoda. The test resource is outside the runtime APK; [fixture identities and hashes](../work/mosques/silencing-stage0-20261028/area-fixtures.md) make the experiment reproducible.
- Temporary app-owned DND rules with a configuration activity, scoped ownership journal and cleanup; the device follow-up adds a finite durable session for actual Modes stop, permission-loss and expiry/boot observations.
- A finite typed location foreground service, actual system-alarm and Play-services geofence routes, session-specific alarms, stop/recovery handling and redacted diagnostics.

The pure model and platform probes are separate feasibility components. This is not an integrated automatic mosque-silencing feature: live GPS was not connected to production prayer policy or a mosque DND request. No editor, user settings migration, production coordinator, collection restart or public service was implemented.

## Completed evidence

Builds ran offline with JDK 21. [Unit results](../work/mosques/silencing-stage0-20261028/unit-results.json): **46 tests, zero failures/errors/skips**. They include 18 centre/accuracy comparisons across the three real shapes, holes/concavity/invalid geometry, the mode truth table, duplicate/stale/mock fixes, every expiry, permission/generation changes, stop/wake suppression and recovery.

Physical checks used one explicitly selected **Pixel 6, Android 16/API 36, build BP4A.251205.006**, with Google Play services. The OnePlus and existing emulators were not used. Exact build identity, APK hashes and restoration evidence are retained in the [validation record](../work/mosques/silencing-stage0-20261028/validation.json).

The final [instrumentation run](../work/mosques/silencing-stage0-20261028/pixel-instrumentation-final.txt) reports 12 discovered tests: **11 checks passed and one deliberate recovery-setup test was skipped** in that normal suite. That setup is handled separately for the process-stop experiment. A successful test-run summary does not make an intentionally skipped setup a completed check.

## Failures found and corrected during Stage 0

Static review caught stale start alarms/geofence callbacks that could restart a stopped diagnostic, and a shared updateable alarm identity that could cause an old release to acquire a newer session's extra. The probe now persists and consumes exact start authorization, invalidates it on stop, and uses immutable session-specific release identities. Focused regression checks passed on the Pixel.

Review also caught main-thread DND recovery waiting behind a long test lock and native button feedback. Recovery runs off the main thread, and probe control click sounds/haptics are disabled. Notification channels explicitly disable sound and vibration; the probe contains no playback or vibration operation.

The [first device suite](../work/mosques/silencing-stage0-20261028/pixel-instrumentation-attempt1.txt) had one failure: a test sampled filter ALL/ringer SILENT immediately after the preceding NONE-rule cleanup, then observed ALL/NORMAL at its end. The phone's external before/after baseline was NORMAL. The diagnostic now requires a filter/ringer/owned-rule observation to remain unchanged for 750 ms within five seconds before comparing baselines; the original final restoration assertion remains. The rerun passed with ALL/NORMAL at both ends. This supports an asynchronous-settling explanation and demonstrates why raw immediate reads are insufficient. The diagnostic wait is not a proposed production restoration strategy.

The failed run and its JSON remain in the evidence folder. No failure was converted into a pass by forcing the phone's global DND or ringer setting.

Follow-up review also required observed DND/exact-access loss to persist local session invalidation, so grant return cannot revive that observed-loss session. Exact-access readiness is checked before reuse, and a delayed boot broadcast must not delete a valid newly created current-boot session. These probe safeguards do not infer a loss/restoration interval that occurred without an observer. Immediate filter/ringer reads also remained transient in the second idle-expiry sample; eventual Zen OFF is not a guaranteed physical audio or settling deadline.

## What the presence experiment establishes

These are exact **logical model outcomes** from accelerated timestamps, assuming code runs at each specified instant:

| Scripted situation after strict entry | Candidate outcome |
|---|---|
| Person remains inside; no usable observations follow | Request ends after **5 minutes**. |
| Person remains inside; only fresh 70 m ambiguous observations continue | Request ends **15 minutes** after last strict support. |
| Person leaves one second after confirmation; the same ambiguous observations continue | Request can persist for **899 seconds after departure**. |
| Two confident outside fixes arrive 20 seconds apart | Request ends at the second outside fix. |
| Strict inside fixes continue throughout | Request still ends at the **3-hour cap**; another inside callback cannot immediately restart it. |

The same ambiguous observations can fit both continued presence and departure. The longer hold reduces the old two-minute release problem but does not resolve that ambiguity. **The proposed 5-minute, 15-minute and 3-hour values are not accepted release defaults.** Field traces are needed to determine whether their premature-release and delayed-release tradeoffs are acceptable, or whether another signal/interaction is required. A coarse geofence EXIT still cannot decide polygon presence.

Model rearm, generation and suppression checks passed. However, this prototype rejects unsupported touching/overlapping multipart topology and certain large/polar/dateline shapes rather than pretending to construct a general union. Those limits must be addressed before a broader supported geometry contract is claimed.

## Why the rest of the plan is a no-go now

1. **No real-mosque field evidence:** indoor strict-inside yield, sustained holding, pass-by, doorway positions and physical departure remain unmeasured. The owner explicitly chose to leave them pending. Current-position fixes and temporary circles cannot substitute for those checks.
2. **No sustained energy comparison:** the phone was powered, and the probe sampled briefly. No comparable TIME_ONLY/idle baseline or sustained visit battery measurement was performed. The diagnostic's frequent sampling cannot validate the proposed release cadence.
3. **Support/recovery limits remain:** the Pixel's actual Modes stop/ordinary-TRUE case, named permission losses, two short forced-idle DND expiries and real reboot/post-unlock cleanup are now measured. Other rule-policy edits, API 29–34, OnePlus/OEM behavior, pre-unlock operation and sustained/shared-alarm quota cases remain open. Force-stop retained NONE until launch in the earlier measured case, and exact-access revocation canceled its release alarm while NONE survived. An unconditional finite restoration guarantee remains unsupported. API 36 component results cannot be generalized to untested environments.

Production manual/nap/wake/recitation/readiness wiring belongs to later stages and was deliberately not attempted; its absence is not itself a failed Stage 0 gate. The component passes do not prove that future integration or physical audio behavior. Sound/vibration output was deliberately not tested, so a restored request journal must not be presented as proof of every audible alarm outcome.

Further work should remain within **Stage 0** until the missing measurements establish a support contract: obtain known-area stationary/entry/exit traces when the owner resumes field checks; test sustained uncertainty/energy and shared-alarm limits; and narrow the offered OS/device envelope accordingly. The completed Pixel user-stop, named permission-loss and post-unlock reboot cases should not be listed as wholly untested. Do not begin the production coordinator/editor or wider feature implementation on the strength of these component passes alone.

## Isolation, cleanup and evidence

The production prayer app was not rebuilt or replaced, and its data was not cleared or seeded. Existing emulators were left alone. The full Tunisia research asset was not changed. The separate probe logs accuracy, fix age, monotonic timestamps, event type and state; it does not persist coordinates, named visits or attendance history.

The **initial** device cleanup and source-integrity results are in [validation.json](../work/mosques/silencing-stage0-20261028/validation.json). At that checkpoint both diagnostic packages were uninstalled after scoped cleanup/evidence retrieval; no current probe rule/service remained, DND was OFF, both ringer modes were NORMAL and sampled vibrator state was IDLE with amplitude zero. Unrelated rule definitions matched the baseline; an already-disabled night schedule's dynamic condition changed from TRUE to FALSE without changing its enabled flag, policy or definition. That condition was recorded, not forcibly restored. The probe was subsequently installed for this device-only follow-up. Historical Zen logs must remain separate from current rule presence. No continuous physical sound recording is claimed.

**Final follow-up cleanup is complete.** The [follow-up validation](../work/mosques/silencing-stage0-device-followup-20261028/validation.json), [final device snapshot](../work/mosques/silencing-stage0-device-followup-20261028/device-after.json), [current Zen configuration](../work/mosques/silencing-stage0-device-followup-20261028/device-after-zen.txt) and [runtime check](../work/mosques/silencing-stage0-device-followup-20261028/post-cleanup-runtime.json) confirm both temporary packages removed, no probe PID/service/current pending alarm/access grant, Zen OFF, both ringer modes NORMAL and sampled vibrator IDLE/amplitude zero. The current Zen configuration exactly matches this follow-up's fresh baseline. All three deliberately changed sound/haptic settings were restored exactly, including removal of the originally absent intensity key; forced idle is off and battery simulation was reset with AC charging reported. Hash checks covered **6,228 preexisting tracked files**: only the plan document changed, no files disappeared and production tracked source remained unchanged. These are scoped restoration and source-integrity observations, not a physical audio test or proof of a battery budget.
