## Scope and implementation

The independent debug app is still `com.tunisianprayertimes.stage0`. The pre-change source archive and before-documents are in the [evidence folder](../work/mosques/silencing-stage0-window-20261031/). Production code, production preferences/data and datasets were not used as a place to install the feature. The Pixel 6/API 36 was explicitly selected; the connected Pixel 9 and OnePlus were not used.

- `WindowScope` accepts existing interval inputs, filters disabled/dismissed occurrences and uses start-inclusive/end-exclusive membership. Only currently containing windows supply a deadline. Overlapping/adjoining intervals retain continuity; any positive gap creates fresh authority.
- `WindowPresence` gates acquisition/evaluation, rejects pre-window/stale fixes, clips acquisition/holding deadlines and discards live presence across a gap. Skip/wake exceptions dismiss supporting occurrences across replans/re-entry. The old independent three-hour cap and six-hour suppression timer were removed.
- Native `WindowAuthority` persists finite accelerated **test-window fixtures**, with boot/generation/clock checks. Service/provider/geofence operations require a live combined-mode token. Native request durations, geofence expiration and release deadlines are clipped to the current window; explicit end cleanup has a real alarm and an in-process cleanup timer.
- Provider cancellation and geofence removal report their API completion separately from logical invalidation. Late callbacks cannot acquire new authority. Cleanup may run after a window without requesting/evaluating location.
- A deliberately named, single-window **synthetic-presence DND fixture** exercises scoped release. Its absolute deadline is clipped after baseline settling and checked again before activation. It does not establish physical mosque presence.

The pure presence layer and native resource layer are separate feasibility components. Real GPS was not wired to production prayer policy or a mosque-DND decision. Native windows were accelerated fixtures, not an edit or end-to-end use of the installed app's prayer settings. A temporary circle centred on an ephemeral current fix is not a mosque boundary or physical arrival/departure.

## Failures and corrections retained

The [first build](../work/mosques/silencing-stage0-window-20261031/build-attempt1.log) caught a Kotlin map-entry typo; it was corrected before installation. The first focused device suite passed before the additional cleanup-only end timer was added. The subsequent [device rerun](../work/mosques/silencing-stage0-window-20261031/pixel-instrumentation-attempt2.txt) had one failing assertion: it required the service's particular timeout label, while the shared window timer had already correctly completed the session 21 ms after the deadline and provider removal 57 ms after it.

The assertion was replaced by behavior checks: the service actually started, completion occurred at the configured end within the named two-second test allowance, provider removal succeeded, the request lifetime was clipped and no accepted fix evaluation crossed the end. Final instrumentation passed. No cleanup bound was relaxed by forcing DND or ringer state. Failed logs remain alongside successful runs.

## Remaining gate

1. **Field behavior:** measure fresh entry yield/latency for someone already indoors at window opening, later arrival, pass-by, holding through poor GPS and physical departure. No existing-inside window confirmation is inherited from before the start; actual silencing can therefore begin late or fail to begin.
2. **Energy:** compare representative window-limited operation with TIME_ONLY/idle, including long user-configured windows. The phone was unplugged for these short trials; charge percentages are not a controlled comparison.
3. **Support/recovery:** retain the [October 28 findings](MOSQUE_SILENCING_STAGE0_REPORT_2026-10-28.md): force-stop/exact-access revocation can leave an owned DND contribution until a supported recovery runs. Two old short forced-idle deliveries are not an upper quota-delay bound. Other OS/OEM versions, natural long idle, all user policy edits and physical audio behavior remain unproved.

Future production scheduler/coordinator/manual/nap/wake/recitation wiring belongs to Stages 1–4. Its absence is not itself a failed Stage 0 gate; these component results simply do not prove that integration. Continue Stage 0 field/energy/support work before changing the broader decision. Catalog completeness/shipping remains outside this stage.
